## Task 3: Deterministic Prioritization Engine ✅ COMPLETE

**Status:** Implemented

**What was created:**

### Files Created:

1. **PrioritizationFlag.java** (com.medscope.intelligence.service)
   - DTO representing one deterministic flag
   - Fields:
     - `InsightType type` - what kind of pattern (SIGNIFICANT_CHANGE, PERSISTENT_ABNORMALITY, TREND_CONTEXT)
     - `InsightPriority priority` - urgency level (HIGH, MODERATE, LOW)
     - `String testName` - canonical test name this flag applies to
     - `List<Long> sourceResultIds` - report_result IDs that support this flag
     - `String evidence` - human-readable explanation of why this was flagged
   - Used as input to AI alongside IntelligenceContext

2. **PrioritizationEngine.java** (com.medscope.intelligence.service)
   - @Component with deterministic rule evaluation
   - Main method: `evaluate(IntelligenceContext context)` returns `List<PrioritizationFlag>`
   - **NO AI INVOLVEMENT** - pure rule-based logic

### Rules Implemented:

**Rule 1: Current Abnormalities** (`evaluateCurrentAbnormalities`)
- Flags any numeric result outside its reference range
- Checks both low and high bounds
- Priority calculation:
  - HIGH: deviation > 30% of reference range
  - MODERATE: deviation ≤ 30% of reference range
- Example flag evidence: "Current value 11.2 g/dL is below range (reference: 13.0-17.0)"
- InsightType: SIGNIFICANT_CHANGE
- sourceResultIds: single current result ID

**Rule 2: Persistent Abnormalities** (`evaluatePersistentAbnormalities`)
- Flags tests that have been abnormal across ≥3 reports
- Requires at least 3 observations total
- Checks historical data from timeline trends
- Priority: always MODERATE
- Example flag evidence: "Hemoglobin has remained outside reference range across 4 reports"
- InsightType: PERSISTENT_ABNORMALITY
- sourceResultIds: all abnormal report_result IDs

**Rule 3: Significant Trends** (`evaluateSignificantTrends`)
- Flags tests with INCREASING or DECREASING trend direction
- Requires at least 3 observations
- Uses Step 6's TrendCalculator output (deterministic, already computed)
- Priority: always LOW (trends need context to determine urgency)
- Example flag evidence: "Glucose shows increasing trend across 5 observations"
- InsightType: TREND_CONTEXT
- sourceResultIds: all observation report_result IDs

### Helper Methods:

- `determinePriority(TestResultContext, abnormalityType)` - calculates HIGH vs MODERATE based on 30% deviation threshold
- `formatRange(low, high)` - formats reference range for evidence strings (handles null bounds)

### Architecture Notes:

- Pure deterministic logic - no external calls, no AI
- Receives IntelligenceContext (assembled by ContextBuilderService)
- Returns flags that AI will use to generate natural-language insights
- Step 6's trend calculations are reused, not recalculated
- Follows step7.txt: "not everything needs AI" - these flags reduce AI workload and improve consistency
- Evidence strings are structured but readable - AI can use them verbatim or rephrase

## Task 5: Intelligence Service Orchestration + REST API ✅ COMPLETE

**Status:** Implemented and tested successfully (102/102 tests passing)

**What was created:**

### Core Service Layer:

1. **IntelligenceService.java** (com.medscope.intelligence.service)
   - Main orchestration service following pattern from Step 5's AnalysisService
   - Orchestrates: context → rules → AI → validation → persist
   - Main methods:
     - `generateInsights(userId, reportId)` - complete generation workflow
     - `getAllInsights(userId)` - retrieve all user insights
     - `getInsightsForReport(userId, reportId)` - retrieve insights for one report

   **Generation Flow:**
   1. **Ownership check** - verify report belongs to user
   2. **Build context** - call ContextBuilderService
   3. **Run rules** - call PrioritizationEngine (deterministic)
   4. **Call AI** - call FastApiIntelligenceClient
   5. **Validate** - call InsightValidator (reject fabricated IDs)
   6. **Persist** - save generation + insights + sources

   **Idempotency:**
   - Follows Step 5 delete-then-insert pattern
   - On regeneration: deletes old insights + sources, creates new generation
   - Generation number increments (1, 2, 3...) for traceability
   - Old generation records retained for history

   **AI Failure Handling:**
   - Creates FAILED generation record
   - Does not affect ReportResult/Analysis/Timeline (frozen data)
   - Returns error message to controller

   **Empty Results:**
   - Creates COMPLETED generation with zero insights
   - Logged but not treated as failure

2. **InsightValidator.java** (com.medscope.intelligence.validation)
   - Critical safety layer preventing fabricated source IDs
   - Validation rules:
     - Rule 1: Must have at least one source result ID
     - Rule 2: Every source result ID must exist in database
     - Rule 3: Title and description must be present
     - Rule 4: Type and priority must be set
   - Invalid insights logged and rejected (not persisted)
   - Follows step7.txt section 7: "If AI returns sourceResultIds: [999999] and result 999999 doesn't exist: REJECT"

### AI Client Layer:

3. **IntelligenceAiClient.java** (com.medscope.intelligence.client)
   - Interface for AI provider abstraction
   - Single method: `generateInsights(context, flags)` → `IntelligenceResponse`
   - Follows step7.txt section 10: "Do not hardwire Step 7 to a provider"

4. **FastApiIntelligenceClient.java** (com.medscope.intelligence.client)
   - Implementation calling FastAPI `/intelligence/generate` endpoint
   - Uses HttpClient with 60-second timeout
   - HTTP/1.1 for uvicorn compatibility (same as Step 5)
   - Jackson ObjectMapper for JSON serialization
   - Error handling: returns FAILED status on exceptions
   - Mirrors pattern from OpenRouterAiServiceClient

5. **GeneratedInsightDto.java** (com.medscope.intelligence.client)
   - DTO for AI response before validation
   - Fields: type, title, description, priority, confidence, sourceResultIds, followUpQuestions

6. **IntelligenceResponse.java** (com.medscope.intelligence.client)
